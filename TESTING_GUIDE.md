# Как проверять конкурентные задачи и программы

Этот гайд — для разработки задач из этого проекта на Go 1.25+.
Основные принципы применимы и к другим конкурентным программам:
нужно проверять результат, порядок событий, безопасность общей памяти
и завершение работы. Один успешный запуск не проверяет всё это сразу.

## 1. Начинай с обещаний программы

Перед тестами прочитай условие и выпиши наблюдаемое поведение.
Не начинай со списка используемых механизмов вроде «проверить mutex».
Тест должен проверять обещание пользователю функции.

Например, для `SharedCall` из задачи 38:

| Обещание | Как его проверить |
| --- | --- |
| `f` запускается один раз | Посчитать вызовы при нескольких `Await` |
| Отмена клиента не отменяет операцию | Отменить одного клиента, проверить состояние операции и результат другого |
| Результат сохраняется | После завершения несколько раз запросить ту же строку и ошибку |
| Уже отменённый клиент получает свою ошибку | Подготовить результат, затем передать отменённый контекст |
| `Close` ждёт завершения `f` | Удержать `f` после получения отмены и проверить, что `Close` ещё не вернулся |
| Повторный `Close` безопасен | Вызвать несколько раз, в том числе конкурентно |

Для другой задачи обещания будут другими. Например, перевод между
счетами должен сохранять общую сумму, а очередь — порядок элементов.
Проверка должна следовать контракту, а не повторять устройство решения.

## 2. Различай четыре вида ошибок

| Вид ошибки | Пример | Чем искать |
| --- | --- | --- |
| Неверный результат | Потерян элемент или возвращена не та ошибка | Проверки значений в тестах |
| Гонка данных, data race | Одна горутина пишет в поле, другая читает без синхронизации | `-race` и анализ доступа к памяти |
| Ошибка порядка событий | Поздний успех заменил первый; `Close` вернулся раньше работы | Управляемые сценарии и проверка состояния |
| Незавершение | Deadlock, зависшая отправка, оставшаяся горутина | Проверки остановки, ограничение времени, стеки |

Гонка данных возникает при несинхронизированных конфликтующих обращениях
к общей памяти, когда хотя бы одно обращение — запись. Детектор видит
только обращения, выполненные при запуске. [Документация Go о race detector](https://go.dev/doc/articles/race_detector).

Ошибка порядка возможна и без гонки данных. Например, mutex защищает
перезапись `generalCause`, но это не делает замену первой причины
второй правильной. Поэтому чистый `-race` не заменяет проверку поведения.

## 3. Рабочий цикл во время решения

1. Выпиши несколько обещаний из условия.
2. Напиши решение и один простой тест успешного сценария.
3. Добавь отдельные сценарии отмены, ошибок и повторных вызовов.
4. Запусти тесты текущей задачи с `-race`.
5. Проверь по коду общую память и все места возможного ожидания.
6. Повтори тесты с разными настройками выполнения, если задача
   зависит от конкурирующих событий.
7. После исправления сохрани тест, который воспроизводил ошибку.
8. Запиши в `notes.md`, что именно проверено и какой командой.

Не нужно каждый раз запускать весь проект 1000 раз. Во время работы
проверяй текущую задачу; перед завершением изменений полезен общий
прогон, если остальные задачи уже готовы к запуску.

## 4. Как устроен обычный тест

Файл называется `solution_test.go`, функции — `Test...` с аргументом
`t *testing.T`. Обычно тест имеет три части:

1. Подготовка: создать объект, контексты, входные данные и каналы.
2. Действие: вызвать метод или запустить нужные вызовы конкурентно.
3. Проверка: сравнить результат с конкретным ожиданием.

Выбирай точность сравнения по контракту. Если функция обязана вернуть
тот же объект ошибки callback, можно сравнить `err == expectedErr`.
Если обёртки ошибки разрешены, используй `errors.Is`.
При требованиях к порядку сравнивай последовательность;
при произвольном порядке — набор результатов с учётом повторений.

В сообщении об ошибке показывай фактическое и ожидаемое значение.
«Получили `context.Canceled`, ожидали `ErrLoad`» полезнее, чем
«неверный результат».

В основной горутине теста `t.Fatal` останавливает дальнейшую проверку,
если продолжать уже бессмысленно. В рабочей горутине не вызывай
`t.Fatal` или `t.FailNow`: передай результат основной горутине либо
используй `t.Error` и корректно заверши worker. Тест должен дождаться
своих горутин до возврата. [Документация testing](https://pkg.go.dev/testing#T.FailNow).

## 5. Управляй событиями, а не угадывай задержки

Плохой способ проверить порядок:

```go
go operation()
time.Sleep(10 * time.Millisecond)
// Предполагаем, что operation уже дошла до нужного места.
```

На твоём компьютере это может работать, а под нагрузкой — нет.
Прошедшее время не сообщает, до какой строки дошла горутина.

Вместо этого передай в заглушку два канала:

```go
started := make(chan struct{})
release := make(chan struct{})

work := func() {
    close(started) // «Я дошёл до этой точки».
    <-release      // «Жду разрешения продолжить».
}

go work()
<-started
// Здесь достоверно известно, что work дошёл до сигнала started.
close(release)
```

Это фрагмент для управления сценарием. В полноценном тесте добавь
сигнал завершения и дождись его: закрытие `release` только разрешает
продолжить, но не доказывает, что worker уже закончил.

Так можно явно задать: «A начал работу → отменили B → разрешили A
вернуть результат». Для проверки обратного порядка нужен другой тест.

Особенно осторожно проверяй, что событие **ещё не произошло**:

```go
select {
case <-returned:
    t.Error("метод вернулся слишком рано")
default:
}
```

Без дополнительной синхронизации это только снимок текущего момента.
Неправильная горутина могла ещё не получить процессор. Для убедительной
проверки сначала дай запущенным горутинам дойти до состояния ожидания.

## 6. Для этого есть testing/synctest

`synctest.Test` создаёт изолированную группу тестовых горутин с
виртуальным временем. `synctest.Wait()` ждёт, пока остальные горутины
этой группы завершатся или окажутся устойчиво заблокированы, например
на каналах, созданных внутри группы. Это удобно для проверки
«вызов всё ещё ждёт». [Документация synctest](https://pkg.go.dev/testing/synctest).

Создавай участвующие в сценарии объекты и каналы внутри
`synctest.Test`. Не считай `Wait` способом перебрать все варианты
планирования или дождаться произвольной внешней операции. Сеть,
файлы и другие внешние ресурсы требуют отдельных проверок.

Пример полноценного теста для задачи 38. Его можно разместить
в её `solution_test.go`; он использует существующий `NewSharedCall`:

```go
package main

import (
    "context"
    "testing"
    "testing/synctest"
)

func TestSharedCallCloseGuide(t *testing.T) {
    synctest.Test(t, func(t *testing.T) {
        cancellationSeen := make(chan struct{})
        release := make(chan struct{})
        returned := make(chan struct{})

        s := NewSharedCall(context.Background(),
            func(ctx context.Context) (string, error) {
                <-ctx.Done()
                close(cancellationSeen)
                <-release // Даже после отмены callback пока работает.
                return "", ctx.Err()
            })

        go func() {
            s.Close()
            close(returned)
        }()

        <-cancellationSeen
        synctest.Wait()

        select {
        case <-returned:
            t.Error("Close вернулся до завершения callback")
        default:
        }

        close(release)
        <-returned
    })
}
```

Здесь проверяются два обещания: `Close` посылает отмену и ждёт
возврата callback. Если убрать ожидание из `Close`, тест поймает
ранний возврат. Если убрать отмену, сценарий зависнет; `synctest`
может обнаружить deadlock внутри группы, а общий `-timeout`
ограничивает длительность запуска.

Для дедлайнов внутри `synctest` можно создать timeout и ждать
`ctx.Done()`. Виртуальное время продвинется, когда горутины группы
устойчиво заблокируются. Бюджет в час не требует реального часа.
Примеры есть в [тестах задачи 36](context/cleanup-after-cancellation/solution_test.go).

## 7. Сделай сам тест безопасным

Тест тоже может содержать гонку. Если callback нескольких горутин
добавляет записи в один slice, защищай журнал mutex или передавай
записи основной горутине через канал. Иначе ошибка теста может
скрыть ошибку решения.

Счётчик вызовов из нескольких горутин удобно делать через
`atomic.Int32`. Для ожидания всех workers подойдёт `WaitGroup`.
Вызови `Add` до запуска соответствующей горутины, а `Done` — при
её завершении. Результаты можно хранить в отдельных элементах среза,
если каждому worker принадлежит свой индекс, сам срез не меняется
и чтение начинается после завершения всех записей.

Если тест выдаёт ошибку раньше конца сценария, его заглушки тоже
нужно остановить: отменить контекст или открыть удерживающий канал,
затем дождаться завершения. Для этого заранее продумай cleanup.
Не делай `t.Fatal` с оставленным worker, который бесконечно ждёт
разрешения от теста.

Не добавляй в тест блокировку вокруг проверяемых вызовов, если
проверяется их конкурентность. Такой тест превратит конкурентное
использование объекта в последовательное и может скрыть проблему.

## 8. Что проверять в сценариях отмены и завершения

Для каждого обещания об отмене полезно рассмотреть события до начала,
во время работы и после готовности результата.

| Сценарий | Что выяснить |
| --- | --- |
| Контекст уже отменён при входе | Должна ли операция вообще начинаться? Какая ошибка обязательна? |
| Отмена во время ожидания | Просыпается ли заблокированный вызов? |
| Результат уже готов, затем отмена | Сохраняется ли результат? Есть ли заданный приоритет? |
| Одновременная отмена и результат | Какие исходы допускает условие? |
| Повторные `Close` или `Cancel` | Безопасны ли повторения и сохраняется ли первая причина? |
| Отмена одного клиента | Кто ещё должен продолжить работу? |
| Возврат метода | Какая работа обязана завершиться до этого момента? |

Для задачи 37 отдельно проверяй ветви, создаваемые **после**
`CancelAll`. Именно переходы между состояниями часто обнаруживают
ошибки, которых нет в обычном успешном примере.

Для каналов проверь пустой и закрытый вход, медленного получателя,
отмену при заблокированной отправке и корректное закрытие выхода.
Для общей памяти — сохранение инварианта: например, сумма балансов
не меняется после переводов, а счётчик не теряет увеличения.

Утечку горутины лучше проверять через её наблюдаемое завершение:
сигнал `finished`, закрытие выходного канала или контракт `Close`.
Сравнение `runtime.NumGoroutine()` до и после теста ненадёжно:
в процессе могут жить посторонние служебные горутины.

## 9. Команды для повседневной работы

Команды запускай из корня проекта. Путь ниже можно заменить
на папку текущей задачи.

```sh
# Быстрый запуск текущей задачи без кеширования результата тестов.
go test -count=1 -timeout=30s ./context/shared-call-independent-cancellation

# Один конкретный тест с подробным выводом.
go test -count=1 -v -run '^TestSharedCallConcurrentCloseWaitsForCallback$' -timeout=30s ./context/shared-call-independent-cancellation

# Проверка конфликтующих обращений к памяти.
go test -race -count=1 -timeout=30s ./context/shared-call-independent-cancellation

# Повторные запуски при разных значениях GOMAXPROCS.
go test -race -count=50 -cpu=1,2,4 -timeout=60s ./context/shared-call-independent-cancellation

# Статический анализ текущей задачи.
go vet ./context/shared-call-independent-cancellation

# Общий прогон, когда остальные задачи готовы.
go test -race -count=1 -timeout=60s ./...
```

`-count` повторяет тесты; `-cpu` меняет число процессоров, одновременно
исполняющих Go-код; `-timeout` ограничивает длительность тестового
процесса пакета. `-run` фильтрует имена тестов — проверь, что нужный
тест действительно запустился. [Флаги go test](https://pkg.go.dev/cmd/go#hdr-Testing_flags).

Повторения увеличивают шанс встретить другие исполнения, но не
гарантируют перебор расписаний. `-shuffle=on` перемешивает порядок
тестов и может обнаружить зависимость от общего состояния;
порядок выполнения горутин внутри теста этот флаг не задаёт.

Таймаут — аварийная граница, а не способ построить сценарий.
Если тест зависает, не начинай с увеличения `-timeout`.
Сначала выясни, какое событие не произошло.

## 10. Как читать неудачный запуск

**Не совпал результат.** Восстанови заданный порядок событий.
Что ожидалось после каждого шага? Добавь промежуточную проверку,
если она поможет локализовать нарушение. Сохрани небольшой сценарий,
а не только большой случайный прогон.

**Появился `WARNING: DATA RACE`.** Найди в отчёте обе конфликтующие
операции и стеки создания горутин. Выясни, чем они должны быть
синхронизированы. Гонка может быть в тестовом журнале, а не в решении.
Блокировка только записи недостаточна, если параллельное чтение
того же значения никак не защищено.

**Тест завис или достиг таймаута.** Посмотри стеки горутин:
какая ждёт канал, какая держит mutex, кто должен подать сигнал?
Для каждого ожидания найди событие, которое его завершает.
Если отправитель ждёт получателя, а получатель — завершения
отправителя, изменение длительности таймаута не исправит проблему.

**Тест падает редко.** Отдельно проверь сам тест: нет ли `Sleep`
для порядка, чтения общего поля без синхронизации или проверки
«ещё не вернулся» до того, как горутина успела запуститься?
Затем воспроизведи нужный порядок каналами и управляемыми заглушками.

## 11. Проверь тесты небольшой намеренной ошибкой

Хороший вопрос: «Если нарушить обещание, этот тест точно упадёт?»

Например, во временной копии решения:

- Убери ожидание из `Close`: тест должен поймать ранний возврат.
- Убери начальную проверку `waiterCtx.Err()`: тест готового результата
  с уже отменённым клиентом должен обнаружить неверный исход.
- Разреши второй запуск `f`: проверка количества вызовов должна упасть.

Делай это в отдельной временной копии, сохраняя рабочее решение.
Для недетерминированной ошибки может понадобиться повторный запуск.
Если тест не падает, проверь, действительно ли он достигает нужного
состояния и проверяет обещание. Не усложняй его без конкретной цели.

## 12. Что остаётся проверить по коду

Тесты проверяют исполненные сценарии. При чтении решения отдельно
разбери следующие вопросы:

- Кто пишет и кто читает каждое общее поле? Какая синхронизация
  связывает эти обращения?
- Кто владеет каналом и закрывает его? Возможно ли двойное закрытие
  или отправка после закрытия?
- Каждое ожидание может завершиться при отмене? Всегда ли найдётся
  отправитель, получатель или освобождающий блокировку вызов?
- Все ли выходы освобождают ресурсы и учитывают запущенные горутины?
- Не удерживается ли mutex во время ожидания работы, которой
  для завершения нужен тот же mutex?
- Сохраняется ли первая ошибка или причина отмены? Не смешана ли
  отмена дочернего контекста с отменой родителя?

В `SharedCall` ключевой порядок такой:
`запись result → закрытие done → получение сигнала → чтение result`.
Он объясняет, почему чтение результата безопасно без mutex.
Если перенести запись после закрытия канала, рассуждение сломается.
[Модель памяти Go](https://go.dev/ref/mem).

Для более крупной программы добавь проверки взаимодействия
компонентов: реальные соединения, остановку сервиса, ограничения
очередей и освобождение ресурсов. Unit-тесты с заглушками удобны
для управления событиями, но не проверяют поведение реального
сетевого клиента. Производительность измеряй отдельно бенчмарками
и профилями: запуск с `-race` не подходит для обычных замеров скорости.

## Что записывать после проверки

В `notes.md` достаточно указать важные сценарии, команду и результат:

> Проверены независимая отмена клиента, сохранение результата,
> приоритет уже отменённого контекста и ожидание callback в Close.
> `go test -race -count=50 -timeout=30s ./context/shared-call-independent-cancellation`
> прошёл без ошибок и сообщений о гонках. Все возможные расписания
> горутин тестами не перебраны.

Так видно, на чём основана оценка корректности и что именно проверялось.
Фраза «тесты проходят» без описания сценариев даёт меньше информации.
