# 017. Слить два канала

## Инсайт

Закрытый вход нельзя оставлять активным в `select`: чтение из него всегда
готово и снова возвращает `ok == false`. В моём решении такой канал заменяется
на `nil`, поэтому его ветка больше не выбирается.

## Решение

Одна горутина выбирает чтение из `a` или `b` и передаёт полученное значение в
небуферизованный выход. Если вход исчерпан, я отключаю его ветку; когда оба
входа отключены, закрываю выход. Порядок каждого источника сохраняется,
поскольку из каждого канала читается последовательно. Дополнительная память —
`O(1)`, вспомогательная горутина одна. Время обработки — `O(na + nb)` для
`na` и `nb` входных значений без учёта ожидания отправителей и потребителя.

## Что важно запомнить

- `nil`-вход изначально не участвует в `select`; если оба входа равны `nil`,
  выход закрывается без значений.
- Порядок между разными источниками не задан и зависит от готовности каналов
  и выбора `select`.
- Выход закрывает его отправитель после исчерпания обоих входов. Чужие входы
  не закрываются.
- Потребитель должен читать выход до закрытия: отмены в этом API нет.

## Проверка

В `solution_test.go` проверяются сохранение порядка и всех значений внутри
каждого источника при произвольном чередовании, один или два `nil`-входа,
ожидание второго источника после закрытия первого и одновременные отправители
на небуферизованных каналах. Демонстрационный пример также завершился и вывел
четыре значения.

```sh
go test -race -timeout 15s ./channel/merge-two-channels
```

Проверка прошла.

## Оценка

Ошибок в текущем решении не обнаружено. Тесты и анализ кода покрывают
перечисленные случаи, но не доказывают корректность для всех расписаний
горутин.
