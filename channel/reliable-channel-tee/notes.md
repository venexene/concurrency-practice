# 018. Разветвитель с гарантией доставки

## Инсайт

Оба выхода должны получить каждое входное значение до перехода к следующему.
Небуферизованные каналы создают нужное обратное давление: медленный читатель
останавливает дальнейшую обработку. При этом ожидание отправки должно
прерываться отменой контекста.

## Решение

Я создаю два небуферизованных канала и одну горутину. Она читает вход через
`select`, затем отправляет значение сначала в `left`, потом в `right`.
При закрытии входа или отмене горутина должна закрыть оба выхода. В обычном
случае порядок в каждом выходе сохраняется, дополнительная память — `O(1)`,
время обработки `n` элементов — `O(n)` без учёта ожидания читателей. Теперь
обе отправки могут прерываться по `ctx.Done()`. При выбранной отмене
`continue` пропускает оставшиеся действия итерации, поэтому прежнее зависание
устранено.

## Что пошло не так

- В предыдущем наброске результаты были объявлены как `chan<- int`: вызывающий
  код не мог бы читать из них, хотя `left` и `right` — выходы функции. В
  текущей версии тип исправлен на `<-chan int`.
- Раньше отправки `lCh <- val` и `rCh <- val` стояли вне `select` с
  `ctx.Done()`.
  Минимальный сценарий: `in` передаёт `7`, читатель `left` получает `7`,
  читатель `right` отсутствует, затем вызывается `cancel()`. Горутина уже
  ждёт на `rCh <- val` и не может заметить отмену. Оба выхода остаются
  открытыми; ожидалось их закрытие без участия читателя `right`.
  `TestTeeCancelWhileWaitingForSecondConsumer` воспроизводил это: через
  секунду после отмены `left` всё ещё не был закрыт. В текущей версии обе
  отправки находятся в `select` с `ctx.Done()`; тест проходит, ошибка
  исправлена.

## Что важно запомнить

- Тип `<-chan int` ограничивает вызывающий код чтением, хотя владелец канала
  внутри `Tee` отправляет в него значения и закрывает его.
- Проверка `ctx.Done()` только при чтении входа не помогает, если горутина
  уже заблокирована на отправке в выходной канал.
- До отмены каждое значение должно попасть в оба выхода; при отмене текущая
  доставка может завершиться лишь для одного из них.
- `continue` внутри `select` переходит к следующей итерации внешнего `for`.
  После установки `finished = true` цикл завершится и оба выхода закроются.

## Проверка

Добавлены тесты обычной доставки и порядка, закрытия пустого входа,
отмены при ожидании входа и отмены при заблокированной отправке. Запуск:

```sh
go test -race -timeout 15s ./channel/reliable-channel-tee
```

Все тесты проходят, сообщений о гонках данных нет. Это проверяет
перечисленные сценарии, но не доказывает корректность при каждом расписании
горутин.
