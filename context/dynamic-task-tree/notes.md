# 040. Группа с динамическими дочерними задачами

## Инсайт

Здесь нужно учитывать два разных времени жизни: всей операции
и каждой отдельной задачи. Возврат `root` завершает только её
саму. Уже принятые дети продолжают работать и могут создавать
своих потомков. Ошибка отменяет дерево, но не означает, что его
задачи уже остановились.

Поэтому решение отдельно отвечает на три вопроса:

- Можно ли конкретному владельцу ещё вызывать свой `spawn`?
- Можно ли дереву вообще принимать новые задачи?
- Завершились ли все задачи, которые уже были приняты?

Один флаг не может корректно ответить на все три вопроса.

## Из каких частей состоит решение

| Состояние | Для чего нужно | Как защищено |
| --- | --- | --- |
| `parentCtx` | Наблюдение за внешней отменой | Сам контекст безопасен для конкурентного использования |
| Общий дочерний `ctx` и `cancel` | Один сигнал остановки для всех задач | Механизм контекста |
| `taskCounter` | Число принятых, но ещё не завершённых задач | `cond.L` |
| `firstErr` | Первая зарегистрированная ошибка дерева | Записи и выбор ошибки под `cond.L` |
| `finished` | Завершился ли владелец конкретного `spawn` | Та же `cond.L`; отдельный флаг для каждого вызова `run` |
| `cond` | Ожидание нулевого счётчика | Проверка условия под `cond.L` |

`finished` — локальная переменная вызова `run`, но её захватывает
замыкание `spawn`. Поэтому сохранённая функция продолжает видеть
этот флаг и после возврата владельца. При этом она не получает
право снова запускать задачи: проверка вернёт `ErrClosed`.

Все задачи получают один и тот же дочерний контекст. Контекст
отдельной задачи больше не создаётся, поэтому успешный возврат
родителя не отменяет ещё работающих детей.

## Как принимается новая задача

Под общей блокировкой `spawn` проверяет условия в определённом порядке:

1. Владелец уже завершился — вернуть `ErrClosed`.
2. Ошибка дерева уже выбрана — вернуть `firstErr`.
3. Родитель отменён, но ошибка ещё не зарегистрирована — сохранить
   `parentCtx.Err()` и отказать с этой ошибкой.
4. Иначе увеличить счётчик: ребёнок принят.

После освобождения блокировки запускается горутина ребёнка,
а `spawn` возвращает `nil`. Не нужно ждать завершения ребёнка
или повторно проверять ошибку после его принятия.

Важен порядок: сначала учёт, затем запуск. Между ними дерево
может отмениться, но ребёнок уже принят и должен быть вызван
ровно один раз с общим, возможно уже отменённым контекстом.
Он обязан отреагировать на отмену, а обёртка — учесть его завершение.

Проверка возможности запуска и увеличение счётчика происходят
под одной блокировкой. Иначе между ними можно было бы закрыть
владельца или завершить учёт дерева.

`ErrClosed` проверяется первым даже после общей отмены. Для завершённого
владельца проблема именно в истёкшем времени жизни его `spawn`.
Работающий владелец вместо этого получает выбранную ошибку дерева.

## Как завершается задача

`run` вызывает callback задачи без удержания общей блокировки.
После возврата callback захватывает mutex и:

1. Устанавливает собственный `finished = true`.
2. Если callback вернул ошибку, а `firstErr` ещё пустая,
   сохраняет её и отменяет общий контекст.
3. Уменьшает `taskCounter` ровно один раз.
4. Вызывает `Broadcast`, чтобы `RunTree` перепроверила счётчик.

Завершение задачи не ждёт её потомков. Они уже учтены независимо
и имеют собственные флаги владельцев.

Callback не выполняется под mutex: он может сам вызвать `spawn`,
ждать ребёнка через собственный канал или ожидать отмену.
Удержание общей блокировки во время этой работы могло бы
заблокировать запуск и завершение остальных задач.

## Почему счётчик не позволяет выйти слишком рано

Сначала счётчик равен `1`: учитывается `root`.
Каждый принятый ребёнок добавляет единицу до запуска.
Каждый завершившийся callback убирает одну единицу.

Например:

```text
root учтена                         counter = 1
root принимает A                    counter = 2
root завершается                    counter = 1
A принимает B                       counter = 2
A завершается                       counter = 1
B завершается                       counter = 0
```

Пока существует задача с живым владельцем `spawn`, она сама
учтена в счётчике. Если она принимает ребёнка, его учёт происходит
до её собственного завершения. При нуле все учтённые владельцы
уже закрыты, и их сохранённые функции `spawn` могут только отказать.

`RunTree` проверяет счётчик в цикле с `cond.Wait()`. Этот вызов
освобождает mutex на время ожидания и захватывает его перед возвратом.
Поэтому задачи могут уменьшать счётчик, а пробуждение не означает
автоматическое завершение дерева: условие проверяется снова.

## Как выбирается первая ошибка

Общее правило: записать ошибку только при `firstErr == nil`.
Так ошибку B не заменят ни ошибка A, ни `context.Canceled`,
которую другой callback вернул в ответ на остановку дерева.

Момент регистрации — изменение общего состояния под mutex.
Если несколько событий конкурируют без заданного порядка,
победит то, которое первым зарегистрировано. Ошибка не выбирается
по имени задачи, глубине дерева или порядку запуска.

После первой ошибки общий контекст отменяется. `spawn` перестаёт
принимать новые задачи, но счётчик не обнуляется искусственно.
Уже принятые задачи должны завершиться сами.

Итоговый результат читается только после завершения всех задач.
Поэтому `RunTree` не возвращает ошибку сразу при её обнаружении.

## Зачем внешняя отмена учитывается в трёх местах

**Обработчик `context.AfterFunc(parentCtx, ...)`** регистрирует отмену
независимо от действий задач. Это нужно, даже если никто больше
не вызывает `spawn`, а callbacks после отмены возвращают `nil`.
Обработчик использует тот же mutex и не заменяет выбранную ошибку.

**Проверка в `spawn`** закрывает промежуток между отменой родителя
и выполнением её асинхронного обработчика. Отмену нельзя игнорировать
только потому, что callback ещё не получил процессор.

**Финальная проверка** не позволяет вернуть `nil`, если родитель
уже отменён, задачи завершились, а обработчик ещё не зарегистрировал
ошибку. Она выполняется только при пустой `firstErr`, поэтому
не заменяет ранее выбранную ошибку задачи.

Важно проверять внешний `parentCtx`, а не общий дочерний `ctx`.
Дочерний контекст отменяется и при ошибке задачи; его `ctx.Err()`
не является самостоятельной внешней ошибкой и не должен заменять
первоначальную причину.

В текущих ветвях отказа `spawn` чтение `firstErr` после `Unlock`
опирается на то, что уже установленная ненулевая ошибка больше
никогда не меняется. Для более очевидного чтения кода можно было
бы сохранить возвращаемую ошибку в локальную переменную под mutex.

## Что пошло не так в процессе

- Сначала использовал одновременно локальные `WaitGroup` и общий
  счётчик. Перешёл к единому учёту всего дерева.
- Ошибки `root` и детей игнорировались, а итог всегда был `nil`.
  Добавил общее состояние первой ошибки и её итоговый возврат.
- В ранних возвратах `spawn` забывал освобождать mutex.
- Ранний выход `run` при отмене сначала не уменьшал счётчик,
  затем уменьшал его без блокировки и уведомления. Кроме того,
  он пропускал уже принятую задачу. Убрал этот отдельный путь:
  callback запускается и проходит общее завершение.
- Создавал контекст для каждого вызова `run`. Возврат родителя
  отменял детей, а ошибка ребёнка не отменяла соседей.
  Перенёс создание общего дочернего контекста в `RunTree`.
- После запуска ребёнка возвращал текущую `firstErr`. Получалось,
  что вызов сообщал об отказе при уже принятой задаче.
  Теперь успешное принятие всегда возвращает `nil`.
- Проверял внешнюю отмену раньше завершения владельца и выбранной
  ошибки. Это нарушало приоритет `ErrClosed` и сохранение первой причины.
- Обработчик внешней отмены сначала записывал ошибку без mutex
  и без проверки предыдущего выбора. Затем аналогичная запись
  вне блокировки оставалась в `spawn`.
- Финальная проверка родителя безусловно возвращала его ошибку,
  заменяя уже выбранную ошибку задачи. Теперь она лишь заполняет
  ещё пустую `firstErr`.

## Проверка

Тесты в `solution_test.go` проверяют:

- Успех и ошибку `root`, её однократный вызов, освобождение общего
  контекста и отсутствие отмены родителя со стороны дерева.
- Отменённый и просроченный родитель до запуска: `root` не вызывается.
- Создание внука после завершения `root`, единый контекст для задач
  и ожидание удерживаемого потомка до возврата `RunTree`.
- Отказ сохранённого `spawn` завершённого владельца во время
  работы дерева и после его завершения; отказанная задача не вызывается.
- Первую ошибку ребёнка, отмену соседа, отказ от новых задач
  и ожидание остановки соседа. Поздняя внешняя отмена и другая
  ошибка не заменяют первоначальную.
- Внешнюю отмену с отказом `spawn`, а также без единого вызова
  `spawn`, когда сама задача возвращает `nil`.
- Сохранение зарегистрированной внешней отмены при поздней ошибке задачи.
- Наследование значений и дедлайна, завершение по внешнему timeout.
- Выполнение всех 100 принятых детей при последующей отмене.
- Сто конкурентных вызовов одного `spawn` и динамических внуков:
  всего выполняется 201 задача с учётом `root`.
- Гонку принятия ребёнка с завершением владельца. Допустимы принятие
  или `ErrClosed`, но число выполненных детей равно числу принятых,
  а принятые удерживаемые дети препятствуют раннему возврату дерева.

Порядок событий задаётся каналами и `testing/synctest`.
Проверки «ещё не вернулся» выполняются после `synctest.Wait()`.
Дедлайн использует виртуальное время.

```sh
go test -race -count=50 -timeout=60s ./context/dynamic-task-tree
go vet ./context/dynamic-task-tree
```

Все 50 прогонов прошли, сообщений о гонках не было.
`go vet` завершился без замечаний. Решение при добавлении тестов
и итоговых заметок не изменялось.

## Ограничение текущей версии

`stop()`, возвращённый `context.AfterFunc`, снимает регистрацию,
если callback ещё не запущен. Он не дожидается уже запущенного callback.
Такой обработчик может ждать mutex и завершиться немного позже
возврата `RunTree`. Ошибку результата это не меняет: выбранная
ненулевая ошибка неизменна, а финальный результат уже вычислен.

Тем не менее текущий `task.md` строго требует завершения всей
служебной работы до возврата. Для полного выполнения этого пункта
нужно отдельно дождаться уже начавшегося обработчика. При этом
нельзя ждать его, удерживая mutex, который ему нужен для завершения.

Тесты подтверждают описанные сценарии выполнения задач и выбора
ошибки, но не гарантируют, что обработчик отмены всегда завершён
именно к моменту возврата функции. Они также не перебирают все
возможные расписания горутин.

## Оценка

Основное поведение дерева подтверждено анализом и тестами.
Остаётся указанная оговорка о строгом завершении callback `AfterFunc`.
Успешный race detector не заменяет проверку этого требования.
