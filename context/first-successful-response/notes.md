# 035. Первый успешный ответ

## Инсайт

Запускаю каждый запрос в своей горутине и жду завершения всех через
`WaitGroup`. `sync.Once` выбирает один успех, а `AllFailed` хранит
ошибки неудачных вызовов по их индексам.

## Решение

Создаю дочерний контекст, канал для результата и канал `done` для
победителя. Каждая горутина перед вызовом проверяет отмену. При
успехе через `sync.Once` ещё раз проверяет, не отменён ли контекст,
затем закрывает `done`, отменяет дочерний контекст и записывает
строку. Ошибка записывается в элемент `AllFailed`, соответствующий
индексу вызова. После `wg.Wait()` возвращаю победивший ответ,
ошибку отмены или `AllFailed`.

Для `n` вызовов запускается `n` горутин, а срез ошибок занимает
`O(n)` памяти. Время зависит от самого долгого вызова, поскольку
метод ждёт все горутины.

## Что пошло не так

- Раньше при успехе закрывал `done`, но не отменял дочерний контекст.
  Если другой вызов ждал `ctx.Done()`, `wg.Wait()` зависал. Теперь
  победитель вызывает `cancel()`; тест остановки проигравшего проходит.
- Раньше внешняя отмена учитывалась только до запуска каждой
  функции. Если все вызовы уже работали, после их остановки метод
  возвращал `AllFailed` вместо `context.Canceled`. Теперь после
  `wg.Wait()` проверяю `ctx.Done()`; тест внешней отмены проходит.
- Затем поздний успех мог победить уже произошедшую внешнюю отмену:
  после `wg.Wait()` проверялся закрытый `done` без учёта порядка
  событий. В тесте контекст отменялся до успешного возврата вызова,
  а результатом было `("late", nil)` вместо
  `("", context.Canceled)`. Теперь внутри регистрации успеха сначала
  проверяется отмена. Если она уже произошла, `done` не закрывается
  и метод возвращает ошибку контекста.

## Что важно запомнить

- Канал `done` виден только обёрткам. Уже работающая функция получает
  сигнал остановки через переданный ей контекст.
- Ошибка одного вызова не должна останавливать другие. Победа
  успешного вызова должна остановить проигравших и дождаться их.
- Проверять отмену нужно при регистрации успеха: проверка двух
  закрытых каналов после `Wait` не восстанавливает их прежний порядок.
- `AllFailed` реализует `error` и хранит ошибки по индексам. Поле
  `errors` сейчас не экспортируется; для чтения причин из другого
  пакета понадобился бы публичный способ доступа.

## Проверка

Тесты проверяют одновременный запуск, успех после отдельной ошибки,
остановку проигравших, порядок ошибок `AllFailed`, внешнюю отмену,
пустую строку как успех и успешный ответ после уже произошедшей
внешней отмены.

`go test -race -count=50 -timeout=20s ./context/first-successful-response`
прошёл без ошибок и сообщений о гонках. Многократный запуск не
доказывает корректность для всех расписаний горутин.

## Оценка

По анализу текущего кода и выполненным тестам ошибок относительно
`task.md` не обнаружено.

## Второй вариант: координатор

Теперь каждый воркер отправляет один `Result` в канал ёмкостью
`len(calls)`, а координатор читает его до закрытия. Закрытие происходит
после `wg.Wait()`, поэтому второй вариант теперь дожидается всех
вызовов перед возвратом. Это исправляет прежний ранний возврат при
успехе и внешней отмене.

Остались две ошибки, видимые в текущем коде:

- При первом успехе вызывается `cancel()` для дочернего `ctx`. После
  закрытия канала финальный `select` видит `<-ctx.Done()` и возвращает
  `ctx.Err()`. Даже единственный успешный вызов даёт
  `("", context.Canceled)` вместо своей строки. Здесь важно различать
  отмену дочернего контекста победителем и внешнюю отмену родителя.
- Каждый успешный `Result` без проверки присваивается `success`.
  Если два вызова вернули успех, более поздний результат в канале
  перезаписывает первый. По условию должен остаться первый
  зарегистрированный успех.

Второй вариант пока оценён по коду. Существующие тесты вызывают
`FirstSuccess`, а не `FirstSuccessCoord`; их результат не проверяет
эти сценарии.
