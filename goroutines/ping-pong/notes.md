# 002. Ping и pong

## Инсайт

Передаю ход между двумя горутинами через каналы. После `ping` отправляю сигнал
для `pong`, после `pong` — для следующего `ping`. Первый сигнал отправляю
из `Ping`, чтобы начать с него.

Теперь `n` хранит только число повторений и не меняется. В каждом методе
свой локальный `i`, поэтому общий счётчик больше не приходится обновлять.

## Что пошло не так

1. **Лишний круг из-за `n >= 0`.** Уменьшаю `n` после `pong`, но при нуле
   всё ещё захожу в цикл. В итоге получается n+1 пар.
   При `n=0` должно быть `[]`, а у меня `["ping", "pong"]`.
   При `n=3` тест получил восемь вызовов вместо шести.
   Исправил: теперь в каждом методе цикл `i < p.n`. При нуле нет ни одного
   вызова, при `n=3` получается ровно три пары.

2. **Общий счётчик оказался с гонкой.** Читаю `p.n` в `Ping`, а меняю его
   в `Pong`. Буфер в `pingCh` позволяет отправке сразу закончиться: `Ping`
   идёт проверять `for p.n >= 0`, пока `Pong` получает сигнал и делает `p.n--`.
   Эти чтение и запись не упорядочены синхронизацией. Race detector поймал
   именно этот конфликт. Чередование вывода само по себе не защищает все
   обращения к счётчику. Исправил: убрал `p.n--`, а счётчик итераций сделал
   локальным для каждой горутины. Теперь `p.n` только читается.

## Что важно запомнить

- Канал упорядочивает действия через отправку и соответствующее получение
  сигнала. Чтение общего поля до ожидания сигнала может остаться с гонкой.
- Последний `pong` тоже отправляет сигнал, хотя `Ping` уже больше не читает.
  В моей версии это работает благодаря буферу размером 1: последний сигнал
  остаётся в канале, и `Pong` может закончить работу.
- При `n=0` начальный сигнал тоже помещается в буфер, а оба цикла пропускаются.
- Работа — O(n) по числу вызовов `emit`, дополнительная память — O(1).
  Сколько времени займёт каждый `emit`, зависит от переданной функции.

## Проверка

В `solution_test.go` проверяются:

- `n=0`, `1`, `3`, `10` и `10000`: ровно n пар, всегда начиная с `ping`.
- Оба порядка запуска: сначала `Ping` и сначала `Pong`.
- Одновременный старт двух методов при `n=1000`.
- Медленный `emit`: следующий вызов должен ждать окончания предыдущего.
- Завершение обоих методов и независимость двух объектов.

В тестах используются каналы и `testing/synctest`, без задержек через
`time.Sleep`. Слайс с результатом защищён Mutex.

```sh
go test -v -race -timeout 30s ./goroutines/ping-pong
```

До исправления тесты падали: получалась лишняя пара, race detector сообщал
о гонке на `p.n`. В проверке медленного `emit` после четырёх разрешённых
вызовов начинался лишний пятый.

После исправления весь набор прошёл: оба порядка запуска, одновременный старт,
медленный `emit`, независимость объектов и все значения n, включая 0 и 10000.
Race detector гонок не нашёл, оба метода завершаются.

## Оценка

Задача решена. Убрал лишнюю итерацию и гонку, сохранив передачу хода через каналы.
