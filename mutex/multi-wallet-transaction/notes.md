# 030. Транзакция над несколькими кошельками

## Инсайт

Для непересекающихся транзакций нужны независимые блокировки кошельков.
Карта может хранить адреса кошельков и после создания использоваться
только для поиска: изменения балансов тогда происходят в отдельных
объектах под их собственными мьютексами.

## Решение

Сейчас храню `map[WalletID]*Wallet`. В `NewLedger` для каждого
начального баланса создаю собственный `Wallet` с балансом и `RWMutex`.
`Apply` собирает ID из `deltas`, сортирует их, затем берёт блокировки
на запись, проверяет балансы и применяет изменения. `Snapshot` копирует
список ID, сортирует его, удаляет повторы, берёт блокировки на чтение
и собирает карту балансов. Блокировки в обоих методах освобождаются через
`defer` при возврате.

Предполагаемая стоимость операций с `k` ID — `O(k log k)` на сортировку
и `O(k)` на обход без учёта ожидания блокировок. Память `Ledger` —
`O(n)` для `n` кошельков; дополнительно `Apply` выделяет срез `O(k)`,
а `Snapshot` — срез и карту `O(k)`. Дополнительных горутин нет.

## Что пошло не так

- Сначала проверка и запись вычисляли `balance - delta`, хотя
  отрицательная `delta` должна списывать, а положительная — зачислять.
  Теперь используется `balance + delta`; знак соответствует условию.
- Сначала `NewLedger` сохранял переданную карту напрямую. Затем я
  применил `maps.Clone` к карте указателей: копировалась только карта,
  но сами `Wallet` оставались общими; сигнатура также не совпадала с
  условием. Теперь `NewLedger` снова принимает `map[WalletID]int64`
  и создаёт отдельный `Wallet` для каждого баланса. Изменение
  исходной карты после создания больше не влияет на `Ledger`.
- Раньше глобальная блокировка сериализовала непересекающиеся
  транзакции. Теперь балансы разнесены по отдельным `Wallet`, а карта
  после создания не меняется. Прежняя гонка при конкурентных записях
  в одну карту балансов этим устранена.
- В промежуточной версии карта мьютексов создавалась через `make`,
  но записи для ID не добавлялись: вызов `Lock` на `nil` приводил к
  панике. Затем мьютексы стали создаваться для каждого ID; теперь
  мьютекс находится в самом `Wallet`.
- В прежней версии `Apply` при отказе освобождал только последний
  захваченный мьютекс. Теперь каждый успешный захват сопровождается
  отложенным освобождением, включая ранний возврат.
- Раньше `Snapshot` отпускал каждый `RLock` сразу после чтения и мог
  смешать состояния до и после транзакции. Теперь удерживает все
  захваченные блокировки до возврата. Оба метода теперь берут
  блокировки в порядке отсортированных ID; `Snapshot` также убирает
  повторы до захвата.
- Раньше в `Apply` срез создавался с длиной `len(deltas)`, а затем
  ID ещё добавлялись через `append`. При `deltas={"A":0}` первый
  пустой ID приводил к панике на `l.wallets[""].mu.Lock()`. Теперь
  длина среза равна нулю, а `len(deltas)` задаёт только ёмкость;
  лишних ID больше нет.
- Раньше `Snapshot([A,A])` дважды пытался взять `RLock` одного
  `RWMutex` до первого `RUnlock`. Если между ними ждал писатель,
  второй `RLock` и писатель ждали друг друга. Теперь после сортировки
  применяю `slices.Compact`: каждый ID блокируется лишь один раз.
- Раньше `Snapshot` сортировал срез вызывающего кода. Например,
  `ids := []WalletID{"B","A"}` после `Snapshot(ids)` менялся на
  `[A,B]`. Теперь сначала вызываю `slices.Clone(ids)` и сортирую
  копию: исходный срез не меняется.

## Что важно запомнить

- `maps.Clone` копирует записи карты, но не копирует объекты, на
  которые указывают её значения.
- `make([]T, n)` сразу создаёт `n` элементов. Для наполнения через
  `append` нужна пустая длина; иначе нулевые значения остаются в начале.
- Одинаковый порядок захвата предотвращает встречное ожидание только
  тогда, когда каждый ID захватывается не более одного раза.
- Перед сортировкой входного среза стоит сделать копию, если метод
  не должен менять данные вызывающего кода.

## Проверка

Добавлены `solution_test.go`: проверены успешный и отклонённый
`Apply`, пустые входы, независимость начальных балансов и снимка,
повторяющиеся ID и сохранность входного среза. Конкурентные тесты
проверяют встречные и непересекающиеся переводы, согласованность
снимков и итоговые балансы.

`go test -race -count=1 -timeout=30s ./mutex/multi-wallet-transaction`
прошёл. Повторный запуск с `-count=10 -timeout=60s` тоже прошёл
без гонок и зависаний. Тесты не доказывают отсутствие ошибок при
каждом возможном расписании горутин; требование о параллельности
непересекающихся операций дополнительно проверено по структуре кода.

## Оценка

По анализу кода и выполненным тестам решение соответствует `task.md`;
неисправленных ошибок не обнаружено. `Apply` меняет балансы только после
проверки всех кошельков под удерживаемыми блокировками, а `Snapshot`
читает свои кошельки под блокировками в общем порядке. Тесты с race
detector прошли, хотя перебрать все расписания горутин невозможно.
