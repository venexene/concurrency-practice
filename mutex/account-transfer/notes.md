# 025. Обмен между счетами

## Инсайт

Для перевода нужно одновременно защитить оба баланса: проверку средств,
списание и зачисление нельзя разрывать. При захвате двух мьютексов нужен
одинаковый порядок для всех переводов, иначе встречные вызовы могут ждать
друг друга.

## Решение

У каждого `Account` есть свой `sync.RWMutex`, баланс `money` и
неизменяемый `id`. В `NewAccount` получаю ID одним вызовом
`idCount.Add(1)`: атомарная операция сразу увеличивает общий счётчик и
возвращает новое значение. `Balance` читает баланс под `RLock`.

В `Transfer` самоперевод обрабатываю под одной блокировкой счёта:
проверяю наличие средств и не меняю баланс. Для двух разных счетов
выбираю порядок захвата мьютексов по `id`, затем под обеими блокировками
проверяю средства и переношу сумму. При успешном переводе общая сумма
сохраняется.

Создание счёта и перевод выполняют `O(1)` работы и используют `O(1)`
дополнительной памяти без учёта ожидания блокировок. Решение не запускает
горутин.

## Что пошло не так

- Сначала `Transfer(a, a, 7)` пытался дважды захватить `a.mu` и зависал
  до проверки средств. Тесты подтвердили зависание при достаточном и
  недостаточном балансе. Теперь самоперевод обрабатывается отдельно;
  оба теста проходят, баланс остаётся прежним.
- Сначала встречные `Transfer(a, b, 3)` и `Transfer(b, a, 4)` могли
  захватить по одному мьютексу и ждать друг друга. Теперь порядок
  захвата зависит от уникального ID счёта, а не от направления перевода.
  Сценарий встречных переводов проходит.
- Первая генерация ID использовала внешний пакет
  `github.com/google/uuid`, запрещённый общими правилами. Затем
  `crypto/rand` убрал зависимость, но не давал строгой гарантии
  уникальности: два одинаковых набора байт дали бы одинаковые ID.
  Сейчас ID выдаёт атомарный счётчик; неиспользуемая зависимость удалена
  из `go.mod`.
- В промежуточной версии сначала вызывался `idCount.Load()`, а затем
  `idCount.Add(1)`. Между этими вызовами две горутины могли обе прочитать
  одно значение и создать счета с одинаковым ID. Теперь используется
  только результат `Add(1)`; тест параллельного создания 1000 счетов
  не нашёл повторов.

## Что важно запомнить

- Блокировка каждого счёта защищает его баланс. Одновременно захваченные
  мьютексы обоих счетов делают проверку и изменение неделимыми для
  конкурентных операций над этими счетами.
- Повторный `Lock` одного мьютекса из той же горутины не работает.
  Самопереводу достаточно одной блокировки.
- Все вызовы выбирают первый мьютекс по одному правилу. Уникальные ID
  задают строгий порядок, который исключает взаимную блокировку
  встречных переводов.
- `Load` и `Add` по отдельности атомарны, но их последовательность
  не является одной неделимой операцией. Для выдачи ID нужен один
  `Add(1)`, возвращающий выделенное значение.

## Проверка

Тесты проверяют обычный перевод, отказ при нехватке средств, сохранение
суммы при одновременных переводах в одном направлении, оба исхода
самоперевода, два встречных перевода и уникальность ID при одновременном
создании 1000 счетов.

```sh
go test -race -timeout 15s ./mutex/account-transfer
go test -race -timeout 30s ./...
```

Оба запуска прошли, race detector не сообщил о гонках. Проверка не
доказывает корректность при всех расписаниях, но прежние сценарии
взаимной блокировки устранены в текущем коде.

## Оценка

Ошибок в текущем решении в пределах проверенного контракта не обнаружено.
